# Mathy Monday repairs: Koios as a projection of the farm

Written during the 2026-06-16 repair session, into the 2026-06-15 Mathy Monday journal, because this is the log slot for the current Koios/upstream refactor thread.

## What I was doing

I came in through `sites/koios.news` because Koios is the content mill we can touch and test, but the real target was upstream orientation.
The recent refactor has been pulling separate packages back toward one spine:

1. relationality admits opaque `Mark`s in `Utterance`s;
2. content, web, games, computing, and production packages project specialized carriers from that bedrock;
3. sites like Koios mount those projections as human/browser-facing surfaces.

The useful repair rule for the day was: when Koios has its own plain record or helper, ask which carrier it is a projection of.
If the answer is "the farm already owns this," Koios should delegate instead of carrying a fork.

## Repair 1: mark opacity at the web boundary

The first runtime failure was a stale import:

```txt
@emsenn/web/server/internal/witness imported markIdentity from
@emsenn/relating/topology
```

That export is gone, and it should stay gone.
The important correction from the human was:

> mark is intentionally opaque within relationality.
> Downstream, if web is the layer that chose what the mark value is, web can care about that value.

So I did not put `markIdentity` back into relationality.
Instead, `services/http-server/src/server/internal/witness.mts` now owns a local downstream comparison for middleware address values.
Relationality still sees only opaque marks; web compares the values it placed into those marks before it crosses back into utterances.

Named concept: **downstream address identity**.
It is not mark identity.
It is a boundary-layer reading over values the boundary layer authored.

I added `services/http-server/src/server/internal/witness.test.mts` to pin this:

- object key order is presentation, not structure;
- array order is structure;
- contrary claims still address the same middleware cell.

This fixed Koios's web-runtime failure without weakening the core invariant.

## Repair 2: Koios demand is not its own engine

`sites/koios.news/src/demand.ts` still contained the old local demand fold:

- seeds;
- view counts;
- Search Console query rows;
- coverage decay;
- score ranking.

But `lib/content-production/src/content-farm/demand.mts` says directly that it was moved from Koios and generalized.
Same math, broader carrier:

- beats are strings instead of a Koios-specific union;
- the frontmatter namespace is a parameter (`termKey`);
- the post shape is a minimal candidate-post carrier.

So I collapsed Koios's demand module into a local projection over the farm carrier.
Koios now owns only:

- the collapse beat vocabulary;
- the seed terms;
- the fact that covered terms live under `frontMatter.koios.seo_term`.

The scoring fold itself now comes from `@emsenn/content-production/content-farm`.

Named concept: **publication-specific projection**.
Koios should not be a second farm; it should be a property/fiber of the farm.

## Current map

The content-production stack now reads like this:

- `@emsenn/content/topology`: demand charges, assignments, drafts, gates, article shapes, copyedit closure, news claim sets.
- `@emsenn/content-production/computer`: ask, demand intake, demand-meets-supply, and production cycles as witness-or-obstruction carriers.
- `@emsenn/content-production/content-farm`: the base cultivation cycle with seams for select, compose, and record.
- `@emsenn/content-production/content-mill`: distribution projections from claim sets to feeds, sitemaps, JSON-LD, h-entry, ninjs, and audits.
- `sites/koios.news`: a publication-specific projection: content store, masthead/theme, beat seeds, newsroom/dashboard, and HTTP routes.

The game/computing connection is no longer just decorative.
Farm cycles carry `DerivationProvenance` from `@emsenn/computing/computer`; the abstract shape is:

```txt
demand/evidence -> observed arena
editorial/LLM procedure -> strategy
draft/gate/deposit -> moves and audit cells
```

The practical slogan: **the content mill is a strategy playing a production game over demand and evidence**, not a CMS script that happens to call an LLM.

## Weird machinery still in the walls

The next obvious seam was the editorial desk.

Koios has `src/desk.ts`, while the farm already has:

- `editorialWorkItem`;
- `depositEditorialWork`;
- `FarmHub`;
- `DeskWitness` / `DeskObstruction`.

That was another duplicated projection, with one useful distinction.
The farm owns the **work item carrier**; Koios still owns the **batch policy** of reading the open board once and depositing only missing withheld posts.

So the repair was:

- `content-farm` now names the smaller `EditorialOffice` shape that `editorialWorkItem` actually needs;
- Koios `deskWorkItems()` now emits `content.farm.work-item` carriers;
- the Koios office identity is `koios.news`, matching the farm property, not the older `koios-news` queue label;
- `enqueueCandidates()` still batches the hub side effect locally.

Named concept: **carrier construction vs side-effect policy**.
The carrier can move upstream without forcing every caller to use the same deposition strategy.

The next seam was configuration:

- Koios seeds are in `src/demand.ts`;
- the farm property config in `package.json` also has seeds;
- `AGENTS.md` and `working/` carry the editor persona/workflow in prose.

The seed duplication is now gone.
At first I admitted the farm property through the package manifest, but that made `package.json` carry arbitrary instance state.
The repair now has an explicit `content-production.config.json` for the farm instance.
`src/demand.ts` reads that document through `contentFarmConfigFromDocument`, then projects the first farm property's seeds and `termKey`.
`SEED_KEYWORDS` is now only a compatibility reading for the newsroom desk.

That config is the publication-property carrier for content production: content store, data store, seed terms, beat sources, Search Console property identity, front-matter namespace, voice, gates, and model.
Credentials and host-local paths remain environment-local; durable non-secret instance configuration lives in the repo.
Search Console readings land in `data/records/search-console.json` and feed the same demand fold as seeds, views, and coverage.

`AGENTS.md`, `working/`, and `memory/` also got a path cleanup.
They now point at `content/posts/` and `dev/docs/journal/`, not the retired `backstage/` and `docs/dev/journal/` paths.
Those files remain operational instructions and state-now readings, not content-production data models.

One upstream package-boundary snag surfaced during verification: `@emsenn/content` had drifted toward importing internal relationality build paths instead of package-committed surfaces.
The repair is to import relating's public topology surface for topology readings, and `@emsenn/relating/articulating/predicating/positing` for charge construction, charge values, and positing vocabulary.
Built files can exist on disk without being lawful downstream commitments.

Named concept: **package export as carrier boundary**.
The compiled module can exist on disk, but if the package boundary does not export it, downstream packages cannot treat it as a lawful projection.

## 2026-06-16: retiring the old local skills

The repo-local `.agents/skills/*` directory was deleted.
Those skills were old ad hoc scripts for package description, package topology, migration, and local agent ritual.
The replacement is not another pile of skill wrappers; it is `@emsenn/jsnode`, which has become the carrier-backed workspace reader.

`jsnode` now gives the useful pieces the old skills were approximating:

- package discovery from the filesystem;
- package facts normalized into `JSNodePackage` and `JSNodeWorkspace` carriers;
- package facts admitted as `Mark`/`Utterance` logs;
- settled workspace topology;
- dependency and ego-graph projections;
- RDF/Turtle/JSON-LD projections;
- package conformance judgments;
- code-documentation cultivation cycles over package surfaces.

I rebuilt `lib/jsnode` and used its own `discoverWorkspace()` plus `workspaceDependencyGraph()` / `egoGraph()` to read the Koios neighbourhood.
The shape is:

```text
koios.news -> content-production -> computing -> games -> relationality
           -> content
           -> web
           -> language
```

That matters for the content mill: Koios is not merely a site plus scripts.
It is a site projection over a content-production layer that already descends through the repo's computing/game system.
The next useful normalization is to make that descent visible in the names and surfaces: a farm tick as finite observation, gate trace, strategy/response, and projection ladder.

A longer note is now in `dev/docs/notes/2026-06-16-jsnode-as-workspace-topology.md`.

I also added the `jsnode-workspace` CLI as a first operator-facing projection of that carrier:

```sh
jsnode-workspace graph --focus @emsenn/koios.news --up 1 --down 3
jsnode-workspace turtle --base https://repo.561.group/
```

The command is intentionally thin: it calls `discoverWorkspace()`, projects with `workspaceDependencyGraph()` / `egoGraph()`, or renders with `workspaceTurtle()`.
So the CLI, a future MCP tool, and a browser surface can share the same carrier read instead of maintaining separate package graph scripts.

## 2026-06-16: deprecating jsnode-server

I started to inspect `services/jsnode-server` as if it were the reusable browser/MCP transport for jsnode.
That was the wrong architectural direction.
The correction is: `@emsenn/jsnode` carries the library and scripts.
If a site or service wants web transport, that host wires the transport from jsnode carriers directly.

So I removed the `services/jsnode-server` submodule from the parent repo and removed 561 Group Operations Manifold's dependency on `@emsenn/jsnode-server`.
561 Group Operations Manifold now owns its small `/jsnode` JSON surface locally:

- `GET /jsnode/health` summarizes the held `JSNodeWorkspace` reading;
- `GET /jsnode/workspace` returns the workspace carrier projection;
- `GET /jsnode/graph` returns the dependency graph projection;
- `/jsnode-bins` still exposes the `@emsenn/jsnode` package scripts, including package-bin discovery and `jsnode-workspace`.

The old `/jsnode/mcp` package-atlas endpoint is gone from 561 Group Operations Manifold.
The Codex hub MCP stays mounted at `/codex/hub/mcp`, and the 561 Group Operations Manifold transport index now advertises Codex MCP, jsnode package-bin/OpenAPI, and host-local jsnode JSON.

Named concept: **transport as host policy**.
A web app, MCP app, OpenAPI app, or browser view may project from `JSNodeWorkspace`, but those projections should live with the host that publishes them.
The carrier package should not become a server package just because one host wanted an HTTP reading.

## Working names from today

- **Judgment carrier**: witness-or-obstruction as a total result shape.
- **Trace vs reading**: append-only logs/surfaces are truth; current state is a fold.
- **Cycle ordinal as clock**: wall time is testimony; order lives in ordinals.
- **Downstream address identity**: boundary-owned value comparison, not core mark identity.
- **Publication-specific projection**: Koios as a property/fiber of the farm, not a separate content-production model.
- **Carrier construction vs side-effect policy**: the farm owns editorial work item shape; Koios may still choose a batch transport policy.
- **Instance config as publication-property carrier**: code-level seed, term-key, Search Console, voice, and source readings should project from `content-production.config.json`, not duplicate them.
- **Package export as carrier boundary**: public subpaths must match the documented carriers downstream packages are allowed to project from.
- **Workspace topology carrier**: package graphs, RDF, conformance, docs, and host-local web views should project from `@emsenn/jsnode` workspace carriers, not from standalone scripts or a reusable `jsnode-server`.
- **Projection ladder**: topology, graph, linked data, HTTP, CLI, MCP, and docs are different readings of the same carrier, not independent models.
- **Transport as host policy**: a site may publish a web/MCP/OpenAPI projection over a carrier, but the transport wiring belongs to that site or service.

The code got less spooky in a useful way: fewer local copies, clearer carrier ownership, and one sharper boundary around what marks mean.

I ran Koios through the real story-production path instead of reasoning about it from the surface.

Pointing Koios at that cable proved the production cycle can get past intake: it selected one witnessed story, made one model call, wrote a draft candidate, judged the gates, and withheld the result.
That run exposed editorial failures, not infrastructure failures: no inline source citations and an overlong description.

But borrowing Filum was the wrong ownership.
Koios.
News is an autonomous publication; its demand fold and farm cycle need their own witnessed intake source.
The repair is now:

- `sites/koios.news/content-production.config.json` declares its own `newscable` with the four collapse wires: climate, finance, politics, and technology;
- each wire owns a Koios-local store under `sites/koios.news/store/<wire>`;
- `src/cable-app.ts` mounts the upstream newscable carrier through Koios's theme;
- `src/cable-server.ts` serves that cable on `cable.koios.news` / port `18809`;
- `src/cable-ingest.ts` ingests the declared RSS sources into those local wire stores;
- `content-production.config.json` now points beat intake at `http://127.0.0.1:18809/newswires/<beat>/`.

Named concept: **intake ownership**.
Demand creates assignments, but witnessed intake is evidence.
If Koios's evidence comes from another site's cable, then Koios is not running its own newsroom game; it is consuming somebody else's claim stream.
A Koios-owned newscable makes the wire stores the publication's evidence substrate, while the farm remains the production strategy over that substrate.

This is not "add another server" as a goal.
The server is only the local transport projection of the carrier Koios was already depending on.
The carrier is the important repair: Koios now owns the wires whose claim-state bundles feed its assignments, gates, run trace, compost, and eventual publication readings.

## 2026-06-16: the editor-in-chief is a topology problem

Today Koios.
News taught me, bluntly, that an autonomous newsroom cannot be developed like a normal publishing app.

The tempting mistake is to keep adding surfaces: another endpoint, another MCP server, another convenience script, another JSON shape that says roughly what the system is doing.
That feels productive in the moment because every new surface can be made to return something.
It is also how the newsroom loses its mind.
A publication like Koios does not become autonomous by accumulating interfaces.
It becomes autonomous when it owns the evidence it acts on, the judgments it makes, and the contradictions it refuses to hide.

The useful break came from relationality.
The lower layer stopped accepting strings and witness records as if they were already relational facts.
That broke content topology in exactly the right place.
A content object had been saying, in effect, "this post is by this communicator" by placing a convenient little record onto the floor and later rebuilding the same strings to read it back.
Relationality now insists on carrier identity: if something is going to enter the topology, it enters as a mark, a token, a claim, an utterance, and then a settled reading.
You do not get to smuggle in a second data model and call it news judgment.

So I changed the content layer to admit content-owned cell marks.
A Koios article relation is now explicitly a content cell: a marked relation between a content object and a coordinate such as message, audience, effect, frame, or gate.
The meme topology still treats the mark as opaque.
The content package, which owns that mark shape, can project it back out for editorial readings.
This is the right split: the core mathematics does not learn what a newsroom is, and the newsroom does not pretend that plain strings are relational carriers.

That sounds abstract, but it changes the job of the editor-in-chief.
The editor is not a dashboard user approving drafts.
The editor is the policy that keeps the carrier honest:

- intake has to be Koios-owned evidence, not borrowed wire copy;
- demand has to assign from witnessed support, not vibes;
- gates have to be charges with evidence, not booleans;
- failure has to remain visible as obstruction, not be collapsed into "try again";
- contrary editorial claims have to be held side by side instead of flattened into a fake consensus.

This is why the local newscable matters.
It is not exciting because it opens a port.
It is exciting because Koios now owns the claim stream that feeds its assignments.
Search Console may someday tell us which public queries deserve attention, but the publication still needs its own intake cable to decide what evidence exists for those terms.
A content mill without evidence ownership is just a prompt loop with a calendar.
Koios needs to be stranger and stricter than that.

I also tightened the no-prophecy gate.
Previously, one prophecy-shaped sentence could still pass while carrying evidence that it needed revision.
That is editorial dishonesty.
If the gate says "no prophecy," one unsupported future- certain sentence is enough to fail.
This is small as code and large as stance: the farm should not publish certainty just because the rest of the draft is usable.
Autonomous production needs a memory for why it withheld a piece, not a habit of sanding down failed judgments until the pipeline turns green.

The larger implication is that Koios.
News is not merely building articles.
It is building a publication game.
Demand is the pressure.
Intake is the board state.
Drafting is a move.
Gate judgment is the rule system.
Compost is memory.
Publication is only one projection of the play.
The editor-in-chief is the strategy that decides which contradictions to carry, which obstructions to respect, and which evidence is strong enough to spend attention on.

That is the standard I need to keep while developing this system.
When a change only makes an endpoint answer, it is probably not enough.
When a change makes the evidence path clearer, the judgment charge more honest, or the newsroom's own production game more legible, it is probably moving Koios in the right direction.

## 2026-06-16: the content mill is not the bottom layer

The most useful correction today was conceptual: Koios.
News should not grow a bespoke private theory of content production.
The deeper stack already has a direction:

```text
relating -> agents -> games -> computing -> content-production -> Koios.News
```

That means when the farm uses `@emsenn/computing`, it is already touching the game layer through computing's projection.
The job is not to bolt "game ideas" onto the content mill after the fact.
The job is to stop reimplementing tiny versions of game/computing concepts inside content-production.

I made one small replacement along those lines.
The farm service used to split a cycle by hand into "observed events" and "audited cells" before stamping the cycle with computing provenance.
Now computing owns that bridge.
The farm hands over labeled outcomes with charge values, and computing promotes them into settled memes, observes the polarized arena, and returns the derivation provenance.
I also kept the full observation on the farm cycle, so future inspection surfaces can read the arena itself instead of only seeing the receipt.

In newsroom terms: Koios says, "this property committed a candidate" or "this property obstructed."
Computing decides how that finite outcome becomes an observed event or audit evidence in the underlying game machinery.

The important name is **publication game**.
Demand is pressure.
Intake is the board state.
Drafting is a move.
Gates are the rule system.
Compost is retained history.
Publication is one projection of play, not the only result worth keeping.

This gives future work a better test.
If I am about to add another content-production-specific shape, I should first ask whether it is actually a labeled observation, a strategy law, a play transition, or a projection of a settled carrier.
If yes, it should probably be parameterized over the relating/agent/game/computing stack instead of becoming another local invention.

A more technical map is in `dev/docs/notes/2026-06-16-publication-game.md`.

## 2026-06-19: nested newsroom departments

The next backend improvement was to stop treating Koios as a blog-shaped package with a few helpers around it.
I added a nested newsroom source model:

```text
src/researching/
  sourcing/
  writing/
    editing/
      publishing/
        managing/
          advertising/
          circulating/
          syndicating/
```

The nesting is intentional.
Researching owns sourcing and demand; writing is the manuscript inventory produced within that research context; editing owns gates and review work; publishing owns public distribution; managing happens after publishing and is split into advertising, circulating, and syndicating.

The live backend now exposes `/departments.json`, whose JSON shape follows the same nested production line:
researching -> writing -> editing -> publishing -> managing.
The public site also exposes `/circulating.json` for feed-native reader return channels and `/syndicating.json` for machine distribution surfaces.
Advertising policy and CSP handling moved out of `src/index.ts` into `publishing/managing/advertising`, so ad insertion is now a managed post-publication concern instead of inline page plumbing.
